# TROPOS 赛题定位校准

核对日期：2026-10-22。官方来源：[2026 FinTechathon 赛事官网](https://fintechathon.g-ican.com/)，国内赛道 → 人工智能赛道 → 银行 AI 智能体。本文将官方要求、代码现状和团队判断分开；不构造评分权重。

## 1. 参赛任务

官方国内人工智能方向要求构建能理解自然语言、规划并执行银行操作的智能体，兼顾办理安全和使用体验。六类场景为智能转账、账单分析、理财操作、卡片管理、订阅／代扣管理、跨场景联动，至少覆盖三类，鼓励完整覆盖。

官网示例和公开首页不是逐条验收标准。部分业务子流程已运行，不代表已经得到赛事确认的完整达标结论。详细交付与评分问题应在 10 月 28 日官方答疑中确认；官网当前列出的人工智能作品提交截止日为 11 月 2 日。

## 2. 本轮判断

上一版首页以手机、旅行、存钱和现金曲线为主，弱化了自然语言办理、用户确认、服务端状态变化和回执。这样的表达容易把 TROPOS 理解为支出管理产品，不能充分呈现赛题要求的业务操作。

项目主线应回到：**知你所想，善作安排——了解用户情况，帮助办理银行事务，情况变化后重新安排，每一步都有明确的确认和记录。**

动态画像、跨期资金计算和生活场景是办理时的判断依据。讲经济学优势时，展示同一笔任务对不同用户、不同状态产生怎样的合理安排，并用记录说明原因；不用增加术语替代业务结果。

四个名字代表职责协作：了解用户、计算规划、检查事件和时机、独立检查授权。当前没有四个自主大模型分别运行的实现，不以首页四个名字暗示该架构。

## 4. 下一步推进顺序

1. **把现有三类业务走顺。** 用统一的“说需求 → 展示依据与步骤 → 单项确认 → 状态／回执”展示。查询分析以可追溯结果结束；需要变更的操作以确认和记录结束。
2. **补自然语言到取消续费的衔接。** 明确哪项订阅，歧义先问，准备待确认事项，再接已有取消接口。不要只把用户从聊天带去另一个页面。
3. **补一条可信的跨业务过程。** 例如查续费 → 比较保留／取消影响 → 用户确认取消 → 账本更新 → 重新计算资金安排。说明每个动作的完成、等待、失败及下一步；重试沿用原请求记录。
4. **再扩一个有完整状态和回执的银行场景。** 优先在模拟卡片限制／解锁与其他银行业务间按赛题答疑和时间选择。只画卡片页面或增加理财推荐文字不计为新增操作能力。

当前应该先把已实现的银行链路做深，让画像和资金计算对真实步骤产生作用，减少继续扩充购物、旅行和装饰性模块的优先级。

## 5. 本轮已调整首页

- 将“知你所想，善作安排”与知己、善谋、择时、守诺提到首页开头。
- 首屏可切换转账、账单分析、订阅管理的办理过程；明确是示例，不产生操作。
- 业务能力先于消费例子展示；资金天气作为后续的差异化说明。
- 移除大块购物／旅行入口，保留完整工作台中的生活规划。
- 沿用本地字体；不把未实现的卡片、理财申赎、后台自动执行或外部下单写成已完成。
